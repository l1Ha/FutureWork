# FutureWork

**用人类之间的交互方式，指挥一切生产力工具。**

未来的工作方式不会是"点鼠标、打命令"，而是"说话、指一下、点点头"。
FutureWork 把这套交互范式提前做成一个可复用的软件接口——
一个面向全平台、全工具的对接核心。

```
    感知层                认知层                 执行层
  ┌──────────┐        ┌──────────┐         ┌──────────┐
  │ 语音     │        │ 意图解析 │         │  窗口    │
  │ 手势     │ ───▶   │ 消歧追问 │ ──────▶  │  文件    │
  │ 面部表情 │        │ 对话状态 │         │  终端    │
  │ 视线     │        │ 安全分级 │         │  浏览器  │
  │ 头动     │        └──────────┘         │  版本控制│
  └──────────┘              ▲              │  MCP 任意│
        │                  │              └──────────┘
        └──── 多模态融合 ───┘                    │
              （冲突仲裁）                        ▼
                                    ┌──────────────────┐
                                    │ 反馈：文字/语音/  │
                                    │ 视觉/触觉        │
                                    └──────────────────┘
```

```python
from futurework.runtime.session import FutureWorkSession
from futurework.types import GestureType

session = FutureWorkSession(workdir="~/my-project")

session.say("把 TODO.md 复制到 backup.md")                       # 说一句就做完
session.say("把这个移到 archive", gesture=GestureType.POINT)     # 边说边指

session.shake()                                                  # 摇头拒绝
session.undo()                                                   # 说错了？撤销
```

## 为什么需要它

人和人沟通时，从来不是一次只用一个通道。你会**边说"把这个挪过去"，
边伸手指向屏幕，视线跟着落在目标上，皱眉表示疑虑**。现有工具的交互模型
恰恰相反：要么点，要么打字，要么敲命令，而且要求你一次只做一件事。

FutureWork 补的正是这一层——**并发信号 → 单一意图**。

它不是又一个语音助手，而是三件可复用基础设施：

1. **多模态融合引擎** —— 处理同意、拒绝、犹豫、注意力四类真实冲突；
2. **意图与对话层** —— 不知道就问，而不是瞎猜；猜错比慢更伤体验；
3. **能力声明式适配器** —— 新工具接入 = 写一个类，不改核心一行代码。

## 核心设计

### 1. 多模态融合：处理冲突，而不是简单加权

人和人交流时的信号经常互相矛盾。FutureWork 的仲裁优先级是
**安全 > 显性 > 隐式**：

| 情况 | 系统行为 |
|---|---|
| 说"删除它" + 摇头 | 识别为冲突 → 降权并追问 |
| 说"删除它" + 点头 | 识别为一致 → 置信度提升 |
| 点头 + 摇头同时出现 | 用户自己也在犹豫 → **立即停手** |
| 皱眉 + 模糊指令 | 主动追问，不执行 |
| 注意力低于阈值 | 先问"现在方便吗"，不贸然动手 |
| 张开手掌 | 无条件中止，优先级最高 |

最后一行尤其重要：**安全信号不能因为"没听懂内容"而失效**——
所以停止手势的判定被放在规则匹配之前。

### 2. 不知道就问

置信度不足时系统绝不猜测，而是生成一句人话追问：

```
「把那个改一下」
  → 我没太明白，可以换个说法吗？比如：打开某个应用、在终端运行命令…

「把那个改一下」+ 指向手势
  → 我看到你指向了「融合锚点」，但不确定要我对它做什么？
    可以说：把它移动到某个目录、复制一份、读取它、或者撤销。
```

追问次数有上限（默认 3 次），超限后给兜底选项，绝不把用户困在循环里。

### 3. 能力声明式适配器

适配器不实现一堆方法，而是**声明自己支持什么**：

```python
class NotionAdapter(ToolAdapter):
    name = "notion"

    def setup(self):
        self.capabilities.declare(Capability(
            action="create_page",
            params={"title": "str", "content": "str?"},
            safety_level=SafetyLevel.SAFE_WRITE,
            description="在 Notion 中创建页面",
        ))

    def _dispatch(self, action, args):
        return notion_api.create(title=args["title"])
```

参数校验、安全分级、异常归一化、撤销记账全部由基类提供。
新增工具成本 ≈ 写一个类。

内置适配器：系统窗口 / 文件系统 / 终端 / 编辑器 / 浏览器 / 版本控制 / MCP。

### 4. 异常处理不是"捕获后忽略"

| 异常类别 | 处理方式 |
|---|---|
| 瞬态（网络抖动、资源占用） | 指数退避重试 + 抖动，**仅对幂等操作重试** |
| 超时 | 强制终止子进程，给出"缩小范围"的建议 |
| 权限不足 | 说明缺什么，引导授权 |
| 资源不存在 | 列出可选项，而不是反复报"找不到" |
| 安全拦截 | 永远不重试，转为向用户解释 |
| 适配器崩溃 | 隔离在适配器内，绝不影响其他工具 |

工具连续失败会触发**熔断**：后续调用立即失败并说明原因，
而不是每次都让用户等满超时。

### 5. 安全：默认安全，但不打断流畅

| 风险等级 | 例子 | 策略 |
|---|---|---|
| `READ_ONLY` | 查看文件、列窗口 | 零打扰直接执行 |
| `SAFE_WRITE` | 写文件（可回滚）、执行普通命令 | 有撤销方案则直接执行 |
| `SENSITIVE_MODIFY` | 关闭窗口、提交代码 | 高置信 + 明确授权才执行 |
| `CRITICAL_DESTRUCTIVE` | 删除文件 | 必须明确授权，且告知不可逆 |

授权可来自**任意模态**：说"是"、点头、捏合手势——只要表达了明确的同意。
但**点头不等于放行**：若系统对指令本身理解不足，仍会再问一次——
此时执行比不执行更危险。

命令行另有危险命令黑名单（`rm -rf /`、`mkfs`、fork 炸弹、强制推送等），
拦截时告诉用户的是**具体是哪一句**，而不是"操作 run_command 被拒绝"。

### 6. 撤销：只读操作不进撤销栈

人的直觉是"撤销刚才那次改动"，不是"撤销刚才那次查看"。
把只读操作也塞进栈里，撤销就会指向错误的那一步。

无法回退的操作（删除文件）会如实告知"不可撤销"，而不是假装成功。

## 性能

在本地文件系统上实测（`examples/benchmark.py`）：

```
【意图理解准确率】
  语料规模   → 42 条中英自然说法
  准确率     → 100.0%（42/42）

【端到端延迟】
  场景                                  均值     P50     P95     P99
  纯语言 · 只读文件                      0.15    0.14    0.17    0.21
  纯语言 · 列目录                        0.14    0.14    0.16    0.16
  纯语言 · 写文件                        0.32    0.19    0.24    0.34
  多模态 · 语音+手势+视线+表情             0.17    0.16    0.18    0.24

【多模态增益：分歧检出】
  语音肯定 + 点头（一致）     → 置信度 0.991，0/4 次要求确认
  语音肯定 + 点头摇头（矛盾） → 置信度 0.716，4/4 次转为追问
```

P95 远低于人类感知流畅阈值（300ms）。延迟主要来自真实 I/O——
把工作目录放在网络卷上时，单次文件操作会额外增加数十毫秒。

## 接入真实硬件

每个感知模块都有**纯函数式信号处理**与**硬件采集**两条路径。
接口不变，换实现即可：

```python
# 语音：换成 Whisper 或云端 ASR
recognizer = SpeechRecognizer(backend=WhisperBackend(model="large-v3"))

# 手势：换成 MediaPipe / 深度学习模型
class MlHandTracker:
    def classify(self, landmarks, *, hand="right"):
        return my_model(landmarks)     # 返回 HandGestureSignal

# 视线：无眼动仪时退化为头部朝向近似
x, y = head_direction_to_screen(yaw, pitch)
```

无硬件时全部走 `Simulated*` 源，因此**离线可测、可回归、可进 CI**。

## 项目结构

```
futurework/
├── types.py              统一数据模型（信号/意图/命令/结果/安全等级）
├── sensory/              感知层
│   ├── speech.py         语音与韵律
│   ├── gesture.py        手势几何识别 + 指向解析
│   ├── facial.py         FACS 表情 + 点头摇头
│   ├── gaze.py           视线追踪、停留判定、元素吸附
│   └── fusion.py         多模态融合、冲突仲裁、工作记忆
├── cognition/            认知层
│   ├── intent.py         规则 + 语义双通道意图解析
│   └── dialogue.py       对话状态机、指代消解、追问
├── tools/                工具层
│   ├── base.py           适配器契约与能力声明
│   ├── system_adapter.py 窗口与应用（Linux/macOS/Windows）
│   ├── filesystem_adapter.py
│   ├── terminal_adapter.py
│   ├── browser_adapter.py
│   ├── vcs_adapter.py
│   ├── mcp_adapter.py    MCP 协议（对接任意外部工具）
│   └── registry.py       路由与可用性巡检
├── resilience/           韧性层
│   ├── errors.py         统一异常分类
│   ├── retry.py          指数退避 + 幂等性约束
│   ├── circuit.py        熔断器
│   ├── undo.py           撤销栈
│   └── safety.py         安全闸门与权限档案
└── runtime/
    ├── orchestrator.py   九阶段编排引擎
    ├── event_bus.py      事件总线
    └── session.py        会话门面
```

一次完整交互经过九个阶段，每个阶段都可独立失败并被隔离：
**感知 → 融合 → 理解 → 对话 → 安全 → 路由 → 执行 → 记账 → 反馈**。

## 设计取舍

几个刻意的选择，以及为什么：

**规则优先于模型。** 安全关键操作必须可预测、可审计。语义通道
（`set_encoder`）作为补充存在，用于泛化没背过的新说法，
但安全动作永远走规则。

**融合不做简单加权平均。** 新增模态会稀释原有信号，而"点头 + 说是"
恰恰是最强的证据组合——所以协同要加成，冲突要扣分。

**归一化不改变大小写。** 文件名在 Linux/macOS 上大小写敏感，
把 `TODO.md` 变成 `todo.md` 会让系统"找不到明明存在的文件"。

**动词要写全。** Python 的 `\w` 匹配汉字，规则里写 `读` 会让
`读取 a.txt` 把"取"当成文件名。

**追问要有限。** 人不会因为对方猜错而愤怒，但会因为对方反复追问而愤怒。
超过上限就给兜底选项。

**失败要说人话。** 错误反馈的目标是"用户知道下一步做什么"，
不是"打印 traceback"。
